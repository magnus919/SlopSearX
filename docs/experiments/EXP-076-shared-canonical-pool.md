# EXP-076: shared canonical complete-pool query and purpose scores

**Status: draft; not registered.** This document authorizes no implementation, provider calls, key access, search, or qualification. Baseline: `c9f2b48437c65c4ebc17f2c7ee18011ae440c119` (repaired current main, 2026-10-05). Issue: #516. The prospective machine protocol is [evidence/EXP-076/protocol.json](evidence/EXP-076/protocol.json); independent design-review requirements are recorded in [evidence/EXP-076/design-review.md](evidence/EXP-076/design-review.md).

## Question and hypothesis

Does assigning both query-relevance Scores and caller-purpose Scores over the same complete, canonical eligible pool, then combining the separate score populations’ full rankings from the shared context with equal-weight reciprocal-rank fusion, improve development ranking quality over the unchanged ordinary W0 ordering while preserving identity, stability, navigation, timing, and resource gates?

The changed mechanism is narrowly defined: query and purpose Score question families share one canonical 80-card state and one composite transaction; there is no first-40 query-score population or native-tail append in the candidate. The existing W0 evaluation remains an independent, fresh comparator and is not a candidate dependency or production fallback. This changes query shared context and response mapping; it does not claim unchanged individual W0 query judgments. On any candidate failure, return the full native/provenance incumbent ordering that existed before Jev.

The hypothesis is that consistent complete-pool context and stable identity-keyed questions remove order-dependent projection as a confound in the dual-score comparison. This is not evidence that more questions improve judgment, that either score is calibrated, or that ranking gains follow.

## What prior evidence does and does not show

EXP-061 canonicalized D/F/E state but stopped before candidate calls; it did not test dual query/purpose Score families and is untested, not a negative candidate result. EXP-062 established byte-stable canonical request construction under its tested permutations, not candidate quality. EXP-065 purpose-only and EXP-072 constrained-purpose comparisons failed the frozen dual-reference gates. EXP-075 completed its 44-call development comparison but was rejected: mean gains were below +.05 under both references, q4 rotation overlap was .1, and q10/q11 targets were absent. This proposal differs by using a shared canonical complete pool for both Score families instead of EXP-075's first-40 query family plus complete purpose family. Earlier failed outcomes remain unchanged and are not regraded.

The exposed EXP-060 tasks and pools are development data only. Even a passing result cannot confirm untouched tasks or pools. q10/q11 targets are absent from the frozen acquisition and cannot be recovered by permutation or reranking; their acquisition-recall gates remain unmet. No further Brave search is proposed or authorized. The recorded Brave budget remains 8/10.

## Frozen candidate and invariance contract

For each operation, make one fresh W0 control using the ordinary first-40 query-only request and retain its full production output for comparison. Make one separate candidate request with the full eligible pool (up to 80 cards) in canonical UTF-8 identity order. The candidate request contains the original query, one shared card state, caller purpose and ordered requested facets, and two namespaced questions per card: `query:<global_id>` and `purpose:<global_id>`. This is 160 questions at 80 cards. Query questions use the ordinary W0 instructions with global ID and ten frozen levels. Purpose questions match the bound capacity projection exactly: `instructions={candidate: dict(card), question: EXP-075 purpose prefix + pinned EXP-072 instructions}` with the four frozen purpose criteria. Candidate score instructions, criteria, normalizations, IDs, and schema are pinned before any implementation or measurement. Both question families see the same complete candidate state; purpose questions retain their frozen purpose rubric.

Global IDs remain attached to their frozen acquired cards. Candidate request bytes, question identity, response mapping, and fused output must be byte/identity invariant under the registered base, repeat, and rotated provenance orders and under reversed, rotated, and deterministic-shuffled source card orders and under shuffled question insertion presented to a canonicalizing builder. The builder must normalize insertion order before serialization. Ties use the existing canonical tuple (URL, title, snippet, global ID) in UTF-8 order. Exact acquired IDs are stable only within these frozen pools: this does not establish invariance when a fresh acquisition reassigns IDs or changes card contents. W0 remains the independent ordinary comparator; do not rewrite its request or judgments.

Each score family produces a separate descending full-pool order from the shared-context response; “separate” describes the score populations, not isolated contexts. Ties use the existing canonical tuple (URL, title, snippet, global ID) in UTF-8 order. The candidate is the full permutation sorted by exact `Fraction(1, 60 + query_rank) + Fraction(1, 60 + purpose_rank)`, then that same canonical tuple. No floating-point score arithmetic, learned weights, post-result rubric edits, question trimming, batching, or tail dropping is permitted. Verify all answer IDs and score ranges, exact membership, full canonical tie behavior, both raw orders, rational scores, fusion, serialized request bytes, and final order. A missing, duplicated, unknown, malformed, or non-finite answer invalidates the whole candidate and falls back to the complete pre-Jev native order.

A capacity-control operation uses a synthetic 80-card inventory and receives no quality credit. Then run the fixed 21 registered real-pool operations from the protocol. Maximum is 44 serial HTTP attempts: two neutral calls and two per registered operation; no retries, extra calls, or searches. A complete, valid 21-operation schedule is required for any quality analysis. A timeout, usage unknown, provider rejection, receipt failure, or other stopping event preserves raw/partial evidence and marks all later operations uninvoked; incomplete schedules receive no quality grade.

## Prospective capacity and resource limits

The runner's reproducible offline projection reports 13 natural pools (largest 59 cards) at 18–118 questions and 36,179–251,111 request bytes with 4,173–34,140-byte state. Its synthetic 80-card/160-question projection is 270,847 request bytes and 10,462-byte state. These are exact serialized-byte measurements for those inputs, not token counts, context fit, or provider acceptance. An authorized neutral 80-card provider transaction could test acceptance of that synthetic shape; it cannot establish natural 80-card capacity or ranking quality. The proposal keeps the bounded 384,000-byte request and 128,000-byte state envelopes while prospectively raising the question cap to 160. The byte caps preserve the declared resource budget, and all 13 observed frozen-pool projections fit; this does not promise every natural 80-card pool fits. An over-bound request is rejected as a study failure and, in any eventual runtime integration, must retain the full native incumbent fallback. Never widen the envelope or trim the pool to force admission. Projection evidence is bound in the machine protocol. Preserve prospective wrapper limits of 384,000 request bytes and 128,000 state bytes; W0 retains the existing 128,000-byte request limit. Whether Jev accepts the 160-question shape and whether natural pools fit model context remain unresolved. A live neutral transaction, if later admitted under an exact registration, can establish acceptance only for that synthetic request shape. Freeze and independently review the exact builder and limits before any later registration. Exceeding a bound or receiving provider rejection is terminal; do not trim, split, or retry.

Retain existing usage budgets (3,000,000 reported input tokens and 160,000 output tokens total) and unknown-usage stop behavior from the frozen EXP-075 accounting contract; raw usage must bind to each physical request/response. These ceilings do not establish affordability or context fit. The candidate phase starts before canonical ordering, state construction, namespacing, and serialization; it includes one HTTP exchange, parsing both score families, exact fusion, and durable final receipt fsync, and must be at most 1,000 ms. The independent W0 phase has its own 1,000 ms maximum. Record whole paired wall time separately. No timing waiver or phase-boundary adjustment is permitted after observing results.

## Evaluation and gates

Use the frozen EXP-064 independent A-v2 and B-v3 references and the existing fixed query-bootstrap method (10,000 draws, seed 6501). Only the eight primary cases q1–q8 contribute to the primary means. Under **each** reference separately, candidate minus W0 mean nDCG@10 must be at least +0.05 and the 95% bootstrap lower bound must be greater than zero. Every primary case must have delta at least −0.03. Candidate top-ten useful-lead count must not be below W0, and every W0 useful facet must remain represented.

Add an explicit useful-source identity guard from the EXP-039 contract, evaluated separately under A and B for every primary case: at most one W0 top-ten source with grade ≥2 may be displaced from candidate top ten. Count and facet retention do not substitute for this identity guard. Repeat and rotated top-ten overlap must each be at least .8 for q1, q4, q7, and q8. For every official target present in q9–q13, candidate rank must be one. Report absent q10/q11 targets as unmet acquisition recall, with no ranking recovery or adoption credit. Require a valid exact full-pool permutation and all answer/rational-score checks. All neutral/resource, usage, deadline, raw-receipt, and stopping gates must pass.

Invariance is separately tested using canonical full-pool request projections for base/repeat/rotate variants and shuffled question insertion orders; with fixed ID-keyed scores, response mapping and fused permutation must also be identical. Include tie fixtures and a complete nonsynthetic-shaped offline analyzer path that exercises both reference assessors and source-closure checks. Synthetic fixtures validate structure only and never establish quality.

## Explicit unresolved acceptance work

This is a proposed development screen, not an implementation or deployment authorization. The existing [complete-pool production acceptance checklist](complete-pool-production-acceptance.md) remains controlling. This proposal adds the EXP-039 identity guard as an explicit development gate; it does not revise the checklist. A future product claim still requires untouched tasks and pools with adequate target acquisition, normalization and evidence for caller-purpose/facet semantics, a reviewed production candidate identity across grouped publication, complete service/cache/singleflight/HTTP/MCP/portal compatibility, and GroktoCrawl X direct/research/sync/SSE/worker/replay propagation. Frozen acquired IDs do not establish fresh-acquisition ID invariance. EXP-076 alone cannot meet q10/q11 acquisition recall or these untouched integration requirements.

## Registration boundary

Before implementing the comparison harness, freeze this candidate design, canonical request projection, score contracts, limits, and gates. Before any provider access, review and qualify the exact committed harness, analyzer, dependencies, and source closure; bind the published endpoint/model bounds (including 64k combined input and 32k state-plus-longest-question), exact byte limits, and remaining provider-acceptance/token-context unknowns; then register the immutable protocol and acquire the required study lease before network or lazy key access. A production selector implementation remains gated on development quality and the untouched-task confirmation. Do not treat offline bytes as token-fit evidence; a bounded live neutral transaction can test provider acceptance of the exact synthetic 160-question request, while natural 80-card fit and quality remain unresolved. If those prerequisites cannot be met without relaxing this protocol, stop as blocked; do not silently change the candidate or gates. A development pass permits only the separately preregistered untouched confirmation and the remaining full production acceptance work under the standing experiment process; it does not itself satisfy those gates.
