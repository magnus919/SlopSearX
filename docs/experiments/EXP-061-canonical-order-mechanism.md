# EXP-061: isolate complete-pool request ordering

Status: design under review; no model or search calls authorized by this document alone. This uses exposed EXP-060 cards and frozen independent references. It is a mechanism study, not fresh confirmation or production acceptance.

## Decision and fixed scope

Determine whether canonical ordering reduces the observed input-order sensitivity without worsening original-purpose relevance or full-pool selection. Preserve the complete W0/D/F/E path, all thirteen cases and twenty-one operation modes, exact membership, caller purpose, facets, model, question contracts, thresholds and existing failure behavior. Do not substitute a D-only product or remove inconvenient cases.

Compare a native arm with a canonical arm. The native arm uses the qualified EXP-060 behavior. The canonical arm sorts the complete D/F/E card state by the UTF-8 byte tuple (URL, title, snippet, stable acquired ID); it never sorts W0, drops cards, splits scoring chunks or edits content. Stable acquired IDs reverse-map to the same native pool. Use canonical order for D ties and E candidate/victim tie resolution. Identical-content duplicates remain separate supplied IDs; the final ID tie-break guarantees invariance only within these frozen identities, not independence from ID reassignment across acquisitions. This experiment makes no general production identity claim.

W0 remains the actual ordinary first-forty query-only contract plus unchanged tail. Acquire one fresh owned W0 response per operation and share that exact response/order across the paired arms so baseline sampling cannot explain the treatment difference. Native and canonical D/F/E calls remain fresh; alternate arm order under a frozen schedule to reduce serial time confounding. Each arm has its original two-second cumulative D/F/E HTTP budget; every single call has its original one-second deadline. One owned sixty-second deadline covers each complete pair, including shared W0 and both candidate arms. The whole study has a four-hour deadline. A failed W0 stops before either candidate arm and preserves both full native incumbent orders. A D/F/E failure atomically returns both members of the pair to the exact complete shared W0 order, discards every proposed action for product output, retains the observed attempts/actions as diagnostic evidence, and halts with the other uninvoked arm and complete future suffix recorded. Unknown usage, malformed membership or exhausted limits follow this same fail-stop rule. Navigation E remains exact shared-W0 bypass.

Keep acquisition order and registered rotation in operation provenance even when treatment request state is canonical. Record the exact canonical request hash, stable-ID mapping, D scores and ranks, F nominees, E sufficiency/addition/loss/action, arm order and owned HTTP receipts. Same-byte repeated provider requests measure remaining variability; request-byte identity by itself does not prove stable scores or better quality.

## Measures and limitations

Run the unchanged A and B quality, useful-count, facet, coverage, navigation and stability checks separately. Also report paired native/canonical changes, per-ID D score variation and each arm's actions. Existing missing navigation targets and insufficient naturally large pools remain failures; they are not repaired or hidden. Maximum owned Jev attempts: 223 (21 shared W0, two sets of 37 D/F and up to 64 E). The shared comparator ledger (W0 and both arms’ D/F) permits 3M known input and 160000 known output tokens, with 64000 input reservation before each call. Each arm’s E retains 3M input / 100000 known output and its original reservation rule. Aggregate actual usage is counted once per owned call, capped at 9M input / 360000 output / 223 attempts / four hours. Shared W0 receipts are referenced by both arms but never double-counted as physical calls. No new searches or Brave calls are needed.

No refinement wording or probability threshold changes in this ordering study. A separate study may test source-selection contribution semantics after this mechanism is understood. Successful exposed diagnostic results still require a frozen candidate and genuinely fresh confirmation across the full original acceptance scope before implementation.
