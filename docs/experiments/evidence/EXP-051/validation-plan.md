# Prospective validation plan

This specifies checks before implementation or grading. It is not a qualification receipt.

## Delivery

Verify frozen input hashes, all six pool memberships and twelve unchanged cases, unique exact original-card joins, and unchanged purposes/facets/selected sets. Derive the before set as after minus added plus removed; require exactly one replacement and the same before set for both cases in each pool. Preserve all 232 cards, including the tail. Metadata remains a separately labeled later lookup; missing identifiers and unresolved records stay explicit. The private abstract-bearing delivery is not a public result artifact.

Every immutable chunk must pass the registered byte bound and contain a pool ID, chunk ordinal/total, hash-bound manifest entry, and terminal marker. Reassembling all chunks must reproduce the entire pool and cases. No shortened card text, hidden dropped fields, fetched pages, or historical reviewer labels are allowed. Actual tool delivery is verified for every chunk before reviewers begin.

## Review validation

Require exactly the twelve registered case IDs, no duplicates, unknown IDs, omitted cases, extra judgments, or invalid enums. Require card/facet memberships to match the registered selected-set union. Evidence pointers must resolve to a visible packet field belonging to the cited card. No reviewer prose can substitute for a missing required typed field.

Compute set-level coverage from each reviewer's own card/facet judgments rather than trusting a separate contradictory yes/no field. Validate each descriptive replacement code against its declared support/lead losses and gains. Preserve uncertainty. Schema or semantic inconsistency invalidates that reviewer record and leaves the study incomplete; do not repair, retry, or replace the record.

## Interpretation

Two complete internally consistent reviewer records establish a usable descriptive reference, not external truth or ranking improvement. Publish disagreement by dimension. Preserve prior EXP-048 outputs unchanged. Further Jev comparisons require separate prospective registration; production adoption still requires the complete acceptance checklist and untouched confirmation.
