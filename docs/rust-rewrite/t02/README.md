## Inactive security proposals (pending explicit compatibility decision)

The separately evaluated, INACTIVE form-body proposal would set the default native form POST admission limit to2MiB (2097152 encoded bytes), checked while buffering, including chunked bodies without Content-Length. Under that proposal, embedders could select another finite usize limit through `native::router_with_form_body_limit`, `serve_with_form_body_limit`, or `serve_with_shutdown_and_form_body_limit`; zero permits only an empty body. These are Rust assembly APIs, not a new environment/config-file field. Under that proposal, oversized form requests would return413 with `error=request_too_large` before parsing or engine dispatch. Other body-transport failures retain400 `invalid_request`. GET and ignored non-form bodies retain their previous handling. This intentionally narrows the original Python buffering domain and requires policy acceptance before promotion.

In the separately evaluated, INACTIVE CSV proposal, structural quoting would remain unchanged for ordinary cells. Cells whose first character after leading ASCII whitespace is `=`, `+`, `-`, or `@`, or whose first character is TAB/CR/LF, would gain a leading literal apostrophe before ordinary CSV escaping. The complete original cell follows that apostrophe. This applies to all five exported fields; it intentionally changes potentially executable spreadsheet cells relative to Python's raw CSV values. It is the declared importer-neutralization policy, not a guarantee for every spreadsheet's interpretation. Existing historical goldens are immutable; security controls are additional Rust expectations, not recaptured Python output.
